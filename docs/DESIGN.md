# แบบระบบ ModelMate

สถานะ: ร่างออกแบบจากข้อกำหนดที่ผู้ใช้ยืนยัน

เอกสารนี้ยังไม่ใช่พฤติกรรมของโปรแกรมที่ implement แล้ว
ตรวจความเป็นไปได้เบื้องต้นกับ Codex CLI 0.169.0 เมื่อ 2026-11-16

## 1. เป้าหมายและขอบเขต

ผู้ใช้สั่งงานครั้งเดียวแล้วคุยปรับงานต่อได้ ระบบเลือก workflow โมเดล
และระดับการคิดให้เหมาะกับแต่ละขั้น โดยตั้งเป้าว่างานต้องผ่านเกณฑ์
และใช้โควตาเท่าที่จำเป็น ไม่ได้ตั้งเป้าให้จำนวน token ต่ำที่สุดอย่างเดียว

รองรับทั้งงานโค้ด วิเคราะห์ วางแผน และเขียนเอกสาร
ใช้เฉพาะ ChatGPT/Codex subscription ผ่านการเข้าสู่ระบบที่รองรับ
แผนเดิมที่ใช้ Python OpenAI SDK และ OPENAI_API_KEY ถูกแทนที่ด้วย App Server

ยังไม่รวมผู้ให้บริการอื่น งานหลาย agent แบบขนาน และ web UI

## 2. สถาปัตยกรรม

```text
Terminal chat
    ↕
Python controller
    ├─ ประเมินโจทย์และเกณฑ์สำเร็จ
    ├─ เลือก workflow / model / reasoning effort
    ├─ ตรวจสิทธิ์ โควตา และจำนวนรอบแก้
    ├─ แสดงความคืบหน้าและคำขออนุมัติ
    └─ เก็บ metadata ของงาน
    ↕ JSON-RPC ผ่าน stdio
Codex App Server
    ├─ ChatGPT authentication
    ├─ Model execution และเครื่องมือที่อนุญาต
    ├─ Threads / history / streaming events
    └─ Model catalog / usage status / approvals
```

รุ่นแรกตั้งเป้าเป็น Python ไฟล์เดียว แยกหน้าที่เป็นฟังก์ชันชัดเจน
ไม่สร้าง framework หรือระบบประวัติสนทนาซ้ำกับ Codex โดยไม่จำเป็น
ตัว controller ต้องตรวจข้อมูลจากโมเดลและ protocol ก่อนใช้ตัดสินใจ

## 3. การประเมินและ routing

อัปเดตตามผู้ใช้ 2026-11-18: ตัด decision model/classifier แยกออกจากขอบเขต
ไม่เรียกโมเดลเพิ่มเพื่อเลือกโมเดลเริ่มต้น และไม่เพิ่มบริการ routing ภายนอก
ใช้แผนที่ผู้ใช้ระบุ, role bindings และกฎตรวจ model/effort/approval ของ controller
เมื่อขอบเขตเปลี่ยน ให้ปรับแผนและตรวจ grants ใหม่ตามกฎเดิม

ข้อมูลที่ต้องได้ก่อนเริ่มงาน:

- เป้าหมายและเกณฑ์สำเร็จ
- ขอบเขต สิ่งที่ห้ามเปลี่ยน และข้อมูลสำคัญที่ยังขาด
- ขั้นงานที่จำเป็นและวิธีตรวจแต่ละขั้น
- โมเดล ระดับการคิด และเหตุผลสั้น ๆ ของแต่ละขั้น

เมื่อข้อมูลสำคัญขาด ให้ถามผู้ใช้ ไม่เพิ่มความเก่งของโมเดลเพื่อเดาขอบเขต
ผลประเมินผิดรูปแบบต้องไม่ทำให้เครื่องมือถูกเรียกหรือสิทธิ์ถูกขยาย

| ลักษณะงาน | เส้นทางเริ่มต้น |
| --- | --- |
| งานเล็ก ขอบเขตชัด | ลงมือ → ตรวจ |
| ต้องตัดสินใจโครงสร้างก่อน | วางแผน → ลงมือ → ตรวจ |
| งานซับซ้อนหรือเสี่ยง | วางแผน → ลงมือ → เครื่องมือและตัวเก่งตรวจ |
| ความยากอยู่ที่การลงมือ | ใช้ตัวเก่งในขั้นลงมือ |
| ผลตรวจไม่ผ่านและไม่คืบหน้า | เสนอแก้ เปลี่ยนแนวทาง หรือยกระดับพร้อมหลักฐาน |

อ่าน model catalog และ supported reasoning efforts จาก Codex
จัดบทบาทประหยัด/กลาง/เก่งตามความสามารถที่มีจริง
การจัดบทบาทและเกณฑ์เลือกต้องทดสอบกับโจทย์จริง ไม่อ้างว่า catalog
รับประกันคุณภาพหรือทำนายการใช้โควตาต่องานได้

## 4. โหมดเลือกโมเดล

| โหมด | พฤติกรรม |
| --- | --- |
| Auto | เลือกและเปลี่ยนเอง พร้อมแจ้งเหตุผล |
| Ask to escalate | ค่าเริ่มต้น ถามก่อนเพิ่มระดับโมเดลหรือการคิด |
| Approve plan | อนุมัติแผนใช้โมเดลก่อนเริ่ม ถามใหม่หากต้องเปลี่ยนแผน |

Ask to escalate ต้องถามด้วยหากงานใหม่จำเป็นต้องเริ่มด้วยตัวเก่ง
การอนุมัติครอบคลุมขั้นงานที่ระบุ ไม่ถือเป็นสิทธิ์ถาวรสำหรับทุกงาน
ผู้ใช้เปลี่ยนโหมดหรือเลือกโมเดลเองได้ระหว่างแชต

## 5. สิทธิ์ลงมือ

สิทธิ์เครื่องมือแยกจากโหมดเลือกโมเดล ผู้ใช้ยืนยันเปลี่ยนนโยบายเมื่อ 2026-11-17
จากถามก่อนทุกคำสั่ง เป็นพฤติกรรม Codex แบบ native:

- ค่าเริ่มต้น read-only sandbox + on-request approvals
- การอ่านและคำสั่งที่ sandbox อนุญาตทำงานได้โดยไม่ถามทุกครั้ง
- การขยายสิทธิ์ใช้คำขออนุมัติของ Codex โดยคงข้อจำกัดเครื่อง/องค์กรที่เข้มกว่า
- แสดงคำสั่ง/cwd หรือ diff ก่อน accept ครั้งเดียว; ไม่มี acceptForSession โดยปริยาย
- ไม่ตีความ timeout, EOF, disconnect หรือ token เก่าเป็นการอนุมัติ
- ไม่อ้างว่า native readable roots จำกัดเฉพาะโฟลเดอร์โปรเจกต์เสมอไป
- คำขอที่ยังไม่รองรับจะหยุด/ปฏิเสธ ไม่อนุมัติโดยเดา schema

ผล printf ที่รันโดยไม่ถามเป็นพฤติกรรมที่ผู้ใช้ยอมรับภายใต้นโยบายใหม่
ไม่ได้แปลว่า workspace-write หรือ full-access เปิดได้เอง
manual live chat เปิดแบบ opt-in เพื่อทดสอบ integration; automated workflow
และการแยก private web context ยังต้องพิสูจน์ตาม gates ของตัวเอง

## 6. สถานะงานและการตรวจ

```text
รับโจทย์ → ชี้แจงถ้าจำเป็น → เลือกขั้นงาน → รออนุมัติถ้าจำเป็น
    → ลงมือ → ตรวจ → ขั้นถัดไป / จบ / แก้ / พัก
```

หลังการลงมือครั้งแรก หากตรวจไม่ผ่าน แก้แล้วตรวจใหม่ได้ไม่เกิน 2 รอบต่อขั้น
จากนั้นหยุดสรุปสิ่งที่ลอง หลักฐานปัญหา และตัวเลือกทำต่อ/เปลี่ยนแนวทาง/พัก
Controller นับรอบเอง โมเดลไม่สามารถรีเซ็ตจำนวนรอบด้วยการเปลี่ยนชื่อขั้น

งานโค้ดตรวจด้วยการทดสอบและเครื่องมือที่เหมาะกับโปรเจกต์
งานเขียนตรวจความครบถ้วน ความสอดคล้อง และแหล่งอ้างอิงเมื่อจำเป็น
ใช้ตัวเก่งตรวจเฉพาะงานซับซ้อนหรือเสี่ยง โดยยังเคารพโหมดอนุมัติยกระดับ

สถานะจบต้องแยกอย่างน้อย: ผ่านเกณฑ์, ทำแล้วแต่ตรวจไม่ครบ, ไม่สำเร็จ, พัก
การอ่านโค้ดหรือการยืนยันจากโมเดลไม่เท่ากับรันทดสอบผ่าน

## 7. โควตาและค่าใช้จ่าย

ใช้ ChatGPT login เท่านั้น ไม่ fallback ไป API key ไม่ซื้อเครดิต
ไม่เปิด Automatic reload และไม่ใช้การเปลี่ยนโมเดลเป็นวิธีหลีกเลี่ยงขีดจำกัด

ก่อนเริ่มขั้นงานใหม่ อ่านสถานะล่าสุดพร้อมเวลาที่อ่าน:

- ใช้โควตารวมใน subscription ได้: ทำต่อตามโหมด
- ถึงขีดจำกัด: บันทึกแล้วพัก
- สถานะไม่ทราบ อ่านไม่ได้ หรือไม่ตรงบัญชี: พักงานอัตโนมัติและแจ้งผู้ใช้

ตรวจทั้งช่วงระยะสั้น รายสัปดาห์ และกลุ่มโควตาที่บริการส่งมา
ไม่ตีความ null เป็นมีโควตา และไม่ถือว่าถึงเวลารีเซ็ตแล้วใช้งานได้แน่นอน
ต้องอ่านสถานะใหม่ก่อนกลับมาทำต่อ

ข้อมูล context window แยกจาก usage quota ไม่ใช้แทนกัน
ไม่แสดงเปอร์เซ็นต์โควตาที่งานจะใช้แบบแม่นยำโดยไม่มีหลักฐาน

ข้อจำกัด: การอ่านสถานะไม่ใช่การจองโควตาหรือ hard spending cap
บัญชีอาจมีการใช้งานพร้อมกันจาก client อื่น และหนึ่ง turn อาจมีหลายคำขอ
ยังไม่พบ request option ที่รับประกันไม่ใช้เครดิตเพิ่มเติมทุกกรณี
ต้องตรวจพฤติกรรมบริการจริงก่อนรับรองข้อกำหนดนี้

## 8. บริบท ประวัติ และการกลับมาทำต่อ

ใช้ thread เดิมในขั้นที่ต้องรักษาบริบท เปลี่ยนโมเดลระหว่าง turn
ไม่คัดลอกประวัติทั้งชุดไปมาเองโดยไม่จำเป็น
การสลับโมเดลยังอาจมีต้นทุนการประมวลผลบริบทและผลต่อ caching

เก็บ metadata ในเครื่องอัตโนมัติ แยกตามโปรเจกต์:

- Codex thread ID และชื่อ session
- เป้าหมาย เกณฑ์สำเร็จ และขั้นงานปัจจุบัน
- จำนวนรอบแก้ โหมด สิทธิ์ที่มีขอบเขตชัดเจน และเหตุผลการพัก
- สรุปสิ่งที่ตัดสินใจ ผลการตรวจ และสิ่งที่ยังไม่เสร็จ

ไม่เก็บสำเนา credentials หรือทำสำเนาประวัติทั้งหมดโดยไม่จำเป็น
กลับมาทำต่อได้ผ่านการเลือก session แต่ต้องตรวจสภาพไฟล์และ process ใหม่
ห้ามรันคำสั่งที่มีผลข้างเคียงซ้ำอัตโนมัติหากไม่ทราบผลครั้งก่อน

การลบต้องแสดง session ที่จะลบและใช้ความสามารถ thread/delete ของ Codex
พร้อมลบ metadata ของเรา Archive ไม่เท่ากับลบ
การลบประวัติไม่ใช่การย้อนการแก้ไฟล์ และไม่รับรองการลบข้อมูลฝั่งบริการทั้งหมด

## 9. การค้นเว็บและข้อมูลส่วนตัว

ค้นข้อมูลสาธารณะได้เองเมื่อจำเป็น พร้อมอ้างอิงแหล่งข้อมูล
ถามก่อนใช้ข้อมูลส่วนตัวจากไฟล์หรือบทสนทนาเป็นคำค้น

แนวทางที่ต้องพิสูจน์:

1. ปิด native web search ในขั้นที่มีบริบทส่วนตัว
2. เตรียมคำค้นโดยส่งข้อมูลออกให้น้อยที่สุด
3. ถ้ามีข้อมูลส่วนตัวหรือไม่แน่ใจ ขออนุมัติก่อนส่ง
4. ขั้นค้นเว็บแยกต่างหากรับเฉพาะข้อมูลที่อนุญาต ไม่รับประวัติส่วนตัวทั้งหมด
5. ส่งผลและแหล่งอ้างอิงกลับมาประกอบงาน

ข้อจำกัด: native hosted web search ไม่มี approval รายคำค้น และไม่ผ่าน
PreToolUse hooks ของเครื่องมือ local ต้องตรวจการแยก filesystem/tools
ของขั้นค้นเว็บจริง ไม่รับประกันจาก prompt อย่างเดียว

## 10. CLI ที่เสนอ

เริ่มด้วย sr หรือ sr "โจทย์"; เมื่อไม่ส่ง prompt ให้เปิดแชตพร้อมคำแนะนำ
ใช้ sr --help เพื่อแสดง usage โดยไม่ต้องล็อกอิน

| คำสั่งในแชต | หน้าที่ |
| --- | --- |
| /status | งาน โมเดล สิทธิ์ โควตา และเวลาอัปเดต |
| /mode | เลือก 3 โหมด routing |
| /permissions | เปลี่ยนสิทธิ์ลงมือ |
| /model | ดูหรือเลือกโมเดลและระดับการคิด |
| /sessions | เลือก session เพื่อทำต่อ |
| /delete | ยืนยันและลบ session |
| /exit | บันทึกแล้วออก |

Ctrl+C ระหว่างทำงานขอหยุด และแสดงว่าหยุดแล้วเมื่อได้รับผลยืนยัน
เหตุผลเลือกโมเดลแสดงสั้น ๆ ไม่แสดง chain-of-thought ภายใน

## 11. แผนพิสูจน์ก่อน implement เต็มรูปแบบ

- [ ] อ่าน account, model catalog และ quota จริงผ่าน App Server
- [ ] สลับโมเดลและ reasoning effort ใน thread เดิม พร้อมตรวจบริบทที่ส่งต่อ
- [ ] ตรวจว่าไม่เกิดคำสั่งหรือการแก้ไฟล์ก่อนอนุมัติในโหมดเริ่มต้น
- [ ] ปฏิเสธหรือยกเลิกคำขออนุมัติแล้วไม่มีผลข้างเคียง
- [ ] พักเมื่อโควตาหมด/อ่านไม่ได้ และไม่ส่งงานซ้ำระหว่างพัก
- [ ] กลับมาทำต่อหลังปิดโปรแกรมโดยไม่ทำคำสั่งซ้ำอย่างไม่ปลอดภัย
- [ ] แยกขั้นค้นเว็บจากข้อมูลส่วนตัวและตรวจช่องทางเครื่องมือที่อาจข้ามข้อจำกัด
- [ ] ตรวจว่าลบ session และ metadata ได้ตามขอบเขตที่แสดง
- [ ] เปรียบเทียบกับการเลือกโมเดลเองบนชุดงานจริงของผู้ใช้

วัดคุณภาพที่ผ่านเกณฑ์ จำนวนรอบแก้ เวลา token usage ที่อ่านได้
และการเปลี่ยนแปลงโควตา โดยระบุว่าการใช้งานจาก client อื่นอาจปนอยู่
ยังไม่มีผล benchmark และยังไม่รับรองการประหยัดโควตา

## 12. หลักฐานและข้อจำกัดการตรวจปัจจุบัน

- ตรวจ CLI version, help และ JSON schema จากเวอร์ชันในเครื่องแล้ว
- ตรวจ source และชุดทดสอบทางการเรื่อง model override, approvals และ rate limits
  แต่ไม่ได้รันชุดทดสอบ upstream หรือ inference กับบัญชีจริง
- ทดลองเปิด App Server ด้วยฐานข้อมูลชั่วคราวและเชื่อม server เดิมแล้ว
  สภาพแวดล้อมตรวจสอบบล็อกด้วย read-only filesystem และ socket permission
- ผู้ใช้ยืนยันว่าใช้ ChatGPT Plus, ใช้ Astra medium ได้,
  ไม่มีเครดิตเพิ่มเติมและไม่ได้เปิด Automatic reload ณ วันที่ตรวจ

## ความคืบหน้าการพัฒนา

เพิ่ม `doctor.py` สำหรับขั้นที่ 1 พร้อม unit tests แล้ว
ตรวจ protocol, pagination, ข้อมูลที่ไม่ควรแสดง, การปฏิเสธ API-key auth,
การหมดเวลาและการปิด subprocess ด้วยข้อมูลจำลอง
ช่อง live account/quota ด้านบนยังไม่ทำเครื่องหมายผ่านจนกว่าจะตรวจบัญชีจริงสำเร็จ

เตรียม `verify.py` สำหรับขั้นที่ 2–3 แล้ว โดย reuse protocol reader จาก doctor
และเปิด method ที่เริ่ม turn ได้เฉพาะคลาสของชุดทดสอบนี้ Doctor ยังคง read-only
unit tests ตรวจกรณี event มาก่อน RPC response, quota ไม่ทราบ,
การตอบ decline, ไม่มี approval event และพบการเขียนไฟล์โดยไม่ได้อนุมัติ

การตรวจสดต้องเปิด `--run-live` และใช้โควตาจริง
ยังไม่ทำเครื่องหมาย checklist ขั้นที่ 2–3 ว่าผ่าน และยังไม่เริ่ม CLI เต็มรูปแบบ
จนกว่าจะมีผลทดสอบสดรองรับขอบเขตสิทธิ์
